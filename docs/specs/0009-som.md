# 0009 — Som

Faz o **Som** acompanhar a Fonte: o do aplicativo quando a Fonte é uma janela, o do sistema inteiro
quando é um monitor (CONTEXT.md). O porquê do caminho técnico — e o que ele arrisca — está na
[ADR 0011](../adr/0011-som-do-aplicativo-pelo-chromium.md). Leia-a antes desta spec.

Esta spec cobre captura, malha, reprodução, diagnóstico e log. Os controles — alternador no seletor,
botão de silenciar, mudo e volume por Transmissor, ícone "sem Som" — são a
[0010](./0010-controles-de-som.md).

**Ordem.** A 0009 é implementada primeiro, e a seção "5. Som" do roteiro manual roda em máquinas de
verdade **antes** de a 0010 começar. Parte do que está aqui vem de leitura de código do Chromium, não
de execução; se o roteiro contrariar a ADR 0011, ela é revista e esta spec junto. As duas specs saem
na mesma release: a 0009 sozinha transmite Som do sistema sem o aviso que a 0010 põe no seletor.

## Invariante: o Som nunca inclui o som do próprio app

É a regra que decide todos os casos duvidosos abaixo. Quando não há como garantir que o som do
Telinha ficou de fora, a Fonte vai **sem Som**. Ela é garantida em cinco pontos, e todos são
obrigatórios:

1. Janela cujo processo é o próprio app (`pid === process.pid` no principal) vai sem Som.
2. Windows anterior ao build 22000 vai sem Som: o Chromium só exclui o próprio processo a partir do
   Windows 11, e no 10 descarta `restrictOwnAudio` em silêncio.
3. Monitor com `track.getSettings().restrictOwnAudio !== true` no renderer tem a track de áudio
   parada e removida da stream.
4. `disable-features=RestrictOwnAudioAddChromiumBack` antes de `app.whenReady()`. Sem isso o
   Chromium remixa na captura o áudio de outros `WebContents` do app.
5. O `<video>` do **próprio** Transmissor no Palco fica sempre mudo. A stream local agora tem áudio,
   e sem isso quem transmite ouve o próprio jogo em dobro.

## Decisão de captura, fora do Electron

A regra de qual áudio pedir é uma função pura em `apps/desktop/src/shared/media/somCapture.ts`,
testada em `somCapture.test.ts`. É a mesma disciplina da ADR 0003: o caso "Windows 10 com a janela
do próprio app" custa uma linha de teste aqui e uma tarde de depuração dentro do handler.

```ts
export const MIN_WINDOWS_BUILD_FOR_SOM = 22000;

export type SomUnavailableReason =
  | "som-off"                  // o Transmissor desligou o Som no seletor (0010)
  | "windows-10"               // build < MIN_WINDOWS_BUILD_FOR_SOM
  | "own-app"                  // a janela é do próprio app
  | "pid-not-found"            // o HWND não resolveu para um processo
  | "capture-failed"           // o Chromium recusou ou entregou a track já encerrada
  | "own-audio-not-excluded";  // monitor sem restrictOwnAudio efetivo

export type SomCaptureMode = "applicationLoopback" | "loopback" | "loopbackWithoutChrome";

export type SomCaptureDecision =
  | { readonly audio: string; readonly mode: SomCaptureMode }
  | { readonly audio: null; readonly reason: SomUnavailableReason };

export interface SomCaptureInput {
  readonly fonteKind: "screen" | "window";
  readonly somRequested: boolean;
  readonly windowsBuild: number;
  readonly pid: number | null;
  readonly ownPid: number;
  readonly forced: boolean;
}

export function decideSomCapture(input: SomCaptureInput): SomCaptureDecision;
/** "10.0.22631" → 22631; qualquer coisa ilegível → 0. */
export function windowsBuildFrom(osRelease: string): number;
/** "window:132456:0" → 132456; "screen:0:0" ou malformado → null. */
export function hwndFromSourceId(sourceId: string): number | null;
```

As regras, em ordem:

| Condição | Resultado |
| --- | --- |
| `!somRequested` | `som-off` |
| `windowsBuild < MIN_WINDOWS_BUILD_FOR_SOM` e `!forced` | `windows-10` |
| janela, `pid === null` ou `pid === 0` | `pid-not-found` |
| janela, `pid === ownPid` | `own-app` — vale **mesmo com `forced`** |
| janela | `applicationLoopback:<pid>`, modo `applicationLoopback` |
| monitor, build ≥ 22000 | `loopback`, modo `loopback` (o renderer pede `restrictOwnAudio`) |
| monitor, build < 22000 com `forced` | `loopbackWithoutChrome`, modo `loopbackWithoutChrome` |

`somRequested` é sempre `true` nesta spec; o alternador que o desliga é da 0010.

### A válvula para testar o Windows 10

`forced` vem de `SCRN_BROADCAST_FORCE_SOM=1`, no mesmo padrão de `shared/hardening.ts`
(`SOM_FORCE_ENV_VAR` e `somForced(env)`, testados lá). Ela existe para o roteiro descobrir, sem
recompilar, se as capturas funcionam no Windows 10. Não é recurso para usuário e não aparece no
README. Se o roteiro mostrar que funcionam, a mudança é `MIN_WINDOWS_BUILD_FOR_SOM` e a ADR 0011, e
a válvula continua como está.

## PID da janela

`apps/desktop/src/main/windowProcess.ts` exporta `processIdOfWindow(hwnd: number): number | null`,
chamando `GetWindowThreadProcessId` do `user32.dll` via [`koffi`](https://koffi.dev). `koffi` entra
em `dependencies` de `apps/desktop` com versão exata.

```ts
import koffi from "koffi";

const user32 = koffi.load("user32.dll");
const GetWindowThreadProcessId = user32.func("__stdcall", "GetWindowThreadProcessId", "uint32", [
  "intptr",
  koffi.out(koffi.pointer("uint32")),
]);

export function processIdOfWindow(hwnd: number): number | null {
  const out = [0];
  GetWindowThreadProcessId(hwnd, out);
  return out[0] || null;
}
```

Confirme a assinatura contra a documentação do koffi da versão instalada: o esboço mostra a forma,
não é contrato. Três regras não negociáveis:

- **Carregamento preguiçoso e protegido.** `koffi.load` roda na primeira chamada, dentro de
  `try/catch`. Uma falha loga `window-process-lookup-failed` com a mensagem e devolve `null`, o que
  vira `pid-not-found`. Nunca derruba o app nem o handler.
- **Sem teste unitário.** É glue nativo, como o `MeshManager`. O que é testável —
  `hwndFromSourceId` e a decisão — já está em `shared`.
- **Empacotado.** O `externalizeDepsPlugin` já deixa `koffi` fora do bundle do principal. Confirme
  no instalador (roteiro, passo "Empacotado") que o `.node` carrega de dentro do `app.asar`. Se não
  carregar, acrescente `asarUnpack: ["**/node_modules/koffi/**"]` ao `electron-builder.yml`.

## Processo principal

**Flag.** Crie `main/somFlags.ts` com `disableOwnAudioMixBack()`, que faz
`app.commandLine.appendSwitch("disable-features", "RestrictOwnAudioAddChromiumBack")`. Chame-a em
`index.ts` ao lado de `enableWindowsGraphicsCapture()`. Nenhum outro ponto do app anexa
`disable-features` hoje. Se algum passar a anexar, os valores precisam ir numa chamada só, porque a
segunda sobrescreve a primeira.

**Handler.** Em `registerDisplayMediaHandler` (`main/index.ts`), depois de o seletor devolver a
Fonte:

1. Se `request.audioRequested` for falso, responda como hoje, só vídeo.
2. Monte a entrada:
   - `fonteKind` pelo prefixo do `source.id`;
   - `pid` por `processIdOfWindow(hwndFromSourceId(source.id))`, só para janela;
   - `ownPid` = `process.pid`;
   - `windowsBuild` de `os.release()`;
   - `forced` de `somForced(process.env)`.
3. `decideSomCapture(...)`.
4. Logue `som-capture-requested` (info) com `fonteKind`, `windowName: source.name`, `pid`,
   `windowsBuild`, `forced`, `somRequested`, e `mode` ou `reason`.
5. Responda `{ video: source, audio: decision.audio }` ou `{ video: source }`. O tipo do Electron
   só aceita `"loopback" | "loopbackWithMute" | WebFrameMain` em `audio`. Faça o cast num único
   ponto, com um comentário apontando a ADR 0011. Esse é o valor não documentado.
6. Guarde `{ fonteKind, decision }` como a última captura, e a Fonte escolhida para o reenvio
   abaixo.

**IPC novo** (`shared/ipc.ts`, `preload/index.ts`, dentro de `ScrnBroadcastApi`):

- `getLastSomCapture(): Promise<SomCaptureReport | null>` devolve `{ fonteKind, decision }` da
  última escolha.
- `retryCaptureWithoutSom(): Promise<boolean>`. Se a última escolha tinha `audio` não nulo, arma um
  reenvio de uso único válido por 10 s: a próxima chamada do handler responde `{ video: fonte }` na
  hora, **sem abrir o seletor**, e loga `som-capture-retry-without-som`. Devolve `true`. Sem escolha
  anterior com áudio (a pessoa cancelou o seletor), devolve `false`.

## Captura no renderer

`media/capture.ts` passa a devolver `Promise<{ stream: MediaStream; som: SomStatus }>`, com
`SomStatus = { ativo: true; mode: SomCaptureMode } | { ativo: false; reason: SomUnavailableReason }`
declarado em `somCapture.ts`.

```ts
navigator.mediaDevices.getDisplayMedia({
  video: { width: { ideal: 1280 }, height: { ideal: 720 }, frameRate: { ideal: 30 } },
  audio: { echoCancellation: false, noiseSuppression: false, autoGainControl: false, restrictOwnAudio: true },
});
```

`restrictOwnAudio` pode faltar nos tipos do `lib.dom`. Declare uma interface local que estende
`MediaTrackConstraints`; nada de `any`. Os três processamentos vão desligados explicitamente, porque
o Chromium os liga por padrão também para áudio de tela, e cancelamento de eco sobre som de jogo o
destrói.

A sequência:

1. **Rejeição.** Se `getDisplayMedia` rejeitar, chame `retryCaptureWithoutSom()`.
   - `true`: logue `som-capture-unavailable` (warn) com `reason: "capture-failed"` e a mensagem do
     erro. Repita o pedido com `audio: false` e siga com `{ ativo: false, reason: "capture-failed" }`.
   - `false`: relance o erro. É cancelamento, e o `useSessao` já trata.
2. **Sem track de áudio.** Busque `getLastSomCapture()` e use o `reason` de lá. Logue
   `som-capture-unavailable` (info).
3. **Track já encerrada** (`readyState === "ended"`). Pare-a, remova-a da stream e trate como
   `capture-failed` (warn).
4. **Monitor em modo `loopback`** com `getSettings().restrictOwnAudio !== true`. Pare a track,
   remova-a e trate como `own-audio-not-excluded`. Logue warn com o `getSettings()` inteiro: é a
   invariante sendo defendida.
5. **Senão:** `track.contentHint = "music"` e log de `som-capture-started` (info) com `mode` e o
   `getSettings()` inteiro. Se algum dos três processamentos continuar `true` nas settings, logue
   também `som-processing-not-disabled` (warn). A track segue, porque é defeito de qualidade e não
   de invariante.
6. **Fim no meio da transmissão.** Escute `ended` na track de áudio e logue `som-capture-ended`
   (info). Isso **não** libera o Palco: o `watchLocalTrack` do `useSessao` continua olhando só o
   vídeo, e o Som parar não é a Fonte parar.

`useSessao` guarda o `SomStatus` em estado (`somStatus`) e o expõe; quem consome é a 0010.

## Malha

Em `MeshManager.createOutgoingConnection`, o laço sobre as tracks passa a distinguir o tipo:

- **vídeo:** como hoje, `applyPreferredCodecs` e `buildEncodingParameters(MAX_BITRATE_BPS)`.
- **áudio:** sem preferência de codec. `applyPreferredCodecs` usa capacidades de vídeo e lançaria
  num transceiver de áudio. Teto `MAX_SOM_BITRATE_BPS = 128_000`, em `shared/media/bitrate.ts`.

**Estéreo.** O Opus do libwebrtc sai mono por padrão, e o encoder do Transmissor só vai para estéreo
se a descrição **remota** que ele recebe tiver `stereo=1`. Ou seja, quem precisa carregar o
parâmetro é a **resposta do Espectador**. Crie `shared/media/opusStereo.ts`:

```ts
/** Acrescenta `stereo=1;sprop-stereo=1;maxaveragebitrate=<n>` ao fmtp de todo payload Opus. */
export function withOpusStereo(sdp: string, maxAverageBitrateBps: number): string;
```

Aplique-a em `applySignal`, no ramo `offer`, sobre a resposta antes do `setLocalDescription`.
Aplique também em `negotiate`, sobre a oferta. Não é o que decide, mas deixa os dois lados
declarando a mesma coisa. Os testes em `opusStereo.test.ts` cobrem:

- fmtp existente ganha os parâmetros;
- `stereo=0` vira `stereo=1`;
- sem `a=fmtp` para o payload Opus, a linha é criada logo após o `a=rtpmap`;
- SDP sem Opus volta idêntico;
- `\r\n` preservado;
- idempotência: aplicar duas vezes dá o mesmo resultado.

Um Espectador em versão antiga não aplica nada disso e recebe mono. Ele não ouve de qualquer jeito.

**`ontrack`.** Com áudio, ele dispara uma vez por track, com a mesma stream. Só o `ended` da track de
**vídeo** chama `onRemoteStreamEnded`, como hoje é implícito por só existir vídeo.

**O que não muda.**
- A escada de reconexão e o watchdog de mídia (`isMediaStalled`) continuam olhando só o vídeo. Som
  parado com vídeo fluindo quase sempre é silêncio de verdade, e renegociar por isso derrubaria
  conexões saudáveis.
- `PROTOCOL_VERSION` não sobe. O Som viaja no SDP, que o sinalizador não lê.

## Diagnóstico

`ConnectionDiagnosticsSnapshot` (`shared/media/diagnostics.ts`) ganha quatro campos:

- `somOutboundBitrateBps` e `somInboundBitrateBps`, de `outbound-rtp`/`inbound-rtp` com
  `kind === "audio"`, pelas chaves `:som-out` e `:som-in` no `bitrateFor`. `forget` limpa as duas.
- `somPacketsLost`, do `inbound-rtp` de áudio.
- `somAudioLevel`: no Transmissor, `audioLevel` do `media-source` de áudio; no Espectador, o
  `audioLevel` do `inbound-rtp` de áudio.

Todos são `null` sem track de áudio. Os testes vão em `diagnostics.test.ts`.

`DiagnosticsPanel` ganha as colunas **Som kbps** e **Som perda**, logo depois de **Perda**. O
`.json` exportado os recebe sem mudança, porque exporta o snapshot inteiro.

**Silêncio prolongado.** Captura bem-sucedida em silêncio é indistinguível de app calado, e é
justamente como o caso da Loja e uma string que parou de funcionar se manifestam (ADR 0011). Crie
`shared/media/somSilence.ts`:

```ts
export const SOM_SILENT_LOG_MS = 60_000;
export const SOM_SILENT_LEVEL = 0.0001;
export class SomSilenceTracker {
  /** Devolve a transição, quando houver uma. `null` em `audioLevel` não conta nem zera. */
  observe(audioLevel: number | null, now: number): "went-silent" | "sound-returned" | null;
  reset(): void;
}
```

O `MeshManager` usa uma instância, alimentada a cada poll de `pollDiagnostics` com o `somAudioLevel`
da **primeira** conexão de papel `transmissor`, porque a track é a mesma em todas. Logue
`som-capture-silent` (info, com `silentForMs`) e `som-capture-sound-returned` (info). Chame `reset()`
em `startTransmitting` e `stopTransmitting`. Não vira aviso na tela.

## Reprodução no Espectador

Quem se ouve é uma função pura em `apps/desktop/src/shared/somSelection.ts`, ao lado de
`palcoSelection.ts`:

```ts
export interface SomAudivelInput {
  readonly modo: ModoPalco;
  readonly stagedId: string | null;
  readonly cellIds: readonly string[];
  readonly myId: string | null;
}
/** Foco: só quem está no Palco. Grade: todas as células. Nunca o próprio Participante. */
export function selectSomAudivel(input: SomAudivelInput): ReadonlySet<string>;
```

A 0010 acrescenta as escolhas manuais a essa mesma função. Os testes em `somSelection.test.ts`
cobrem:

- Foco com dois Transmissores ouve só o Palco;
- promover a miniatura troca quem se ouve;
- Grade ouve os dois;
- o próprio Transmissor nunca entra, nem no Palco nem na Grade;
- Palco vazio devolve conjunto vazio.

Em `SessaoScreen`, um efeito aplica o resultado: para cada id de `streamsById`,
`surfaceOf(id).muted = !audivel.has(id)`.

Em `media/videoSurfaces.ts`:
- O elemento continua nascendo com `muted = true`. Atualize o comentário, porque a razão agora é
  "mudo até o Palco decidir", não "áudio não existe".
- `attach` não mexe em `muted`: a reanexação do vigia não pode religar ninguém.
- No `catch` do `play()`, um erro `NotAllowedError` loga `som-playback-blocked` (warn, com o `id`).
  É a única forma de ver o autoplay recusando áudio. Os outros erros continuam ignorados, pelo motivo
  já comentado.

O `autoplayPolicy` padrão do Electron já é `no-user-gesture-required`, e `mainWindow.ts` não o muda.
Não acrescente a opção.

## Seletor de Fonte

Só o texto, nesta spec. O subtítulo "O áudio do sistema não é compartilhado." vira
**"Janelas levam o Som do aplicativo; monitores, o do sistema."**. A 0010 substitui isso pelo
alternador e pelo aviso.

## Roteiro manual

Acrescente a seção **"5. Som"** a
[roteiro-de-testes-manuais-de-midia.md](../roteiro-de-testes-manuais-de-midia.md), no formato das
seções existentes: passo, **O que observar**, e **Se falhar** apontando o evento de log. Os casos:

1. **Janela com Som (Windows 11).** Transmita a janela de um player tocando áudio enquanto outro
   app toca outra coisa ao mesmo tempo. O Espectador ouve só a janela transmitida. O log mostra
   `som-capture-requested { mode: 'applicationLoopback' }` e `som-capture-started` com os três
   processamentos em `false`.
2. **Estéreo.** Um vídeo de teste de canal esquerdo e direito, ouvido de fone no Espectador.
3. **Monitor sem o próprio Telinha. Duas máquinas.** Na mesma máquina, a instância B é outro
   processo, e o som dela entra legitimamente no Som do sistema de A. A e B transmitem monitor, e A
   põe B no Palco, de modo que o Som de B toca na máquina de A. B não ouve o próprio Som voltando
   pela transmissão de A.
4. **Janela do próprio Telinha.** Vai sem Som, com `reason: 'own-app'`.
5. **Windows 10, sem válvula.** Vai sem Som, com `reason: 'windows-10'`.
6. **Windows 10, com `SCRN_BROADCAST_FORCE_SOM=1`.** Repita 1 e 3 e registre três coisas: se há
   Som, se o Discord ou outro app vaza na janela, e se o som do Telinha vaza no monitor.
7. **App da Loja.** Transmita um app da Microsoft Store tocando áudio. Registre se chega silêncio,
   e se `som-capture-silent` aparece depois de 60 s.
8. **Palco.** Com dois Transmissores:
   - no Foco, só se ouve quem está no Palco;
   - promover a miniatura troca o Som;
   - na Grade, ouvem-se os dois;
   - a própria Fonte de quem transmite nunca toca na máquina dele.
9. **Versão antiga.** Um Espectador com o instalador anterior entra, vê a Fonte, não quebra e não
   ouve.
10. **Custo.** Com 6 Espectadores, a coluna Som kbps fica perto de 128 em cada conexão. Anote a CPU
    do processo do Transmissor no Gerenciador de Tarefas com e sem Som. A ADR 0002 contabiliza +0,77
    Mbps; se a CPU passar de 10% de um núcleo, anote na ADR 0011.
11. **Empacotado.** No app instalado, `som-capture-requested` de uma janela traz `pid` não nulo. Isso
    prova que o `koffi` carregou de dentro do asar.

**Portão.** Registre na ADR 0011 o resultado dos casos 3, 6 e 7, trocando "Validação pendente" pelo
que foi observado e quando. Se contrariarem a ADR, ela é revista antes de a 0010 começar.

  os casos novos de `diagnostics` e o `somForced` de `hardening`.
